0.1讲解这项研究到底在做什么

这份教程，本质上是把一篇真实论文拆开讲给你听。案例是《基于情感演化图谱的网络暴力事件防范与治理研究——“刘学州事件”》：2022 年初，曾发布寻亲视频的少年刘学州留下遗书离世，微博评论区围绕此事争论了约 80 天。研究让电脑替我们读完这 30,235 条有效评论，回答三个问题——大家在不同阶段在吵什么（主题怎么迁移）、越吵越凶还是渐渐平息（生命周期）、情绪怎么变化（情感），最终产出一张情感演化图谱，并给出分阶段治理建议。

1.1讲解为什么第一步永远是「整理」

想象你组织了一场 500 人的线下座谈会，请了速记员。会后你拿到 500 页速记稿，里面混着：「@某某 你快看这条」「转发微博」「http://t.cn/xxxx」「哈哈哈哈哈哈」「[doge][doge]」……你要做研究，得先把这些噪音挑出去，留下真正表达观点的句子。

微博评论区就是这场座谈会。原始数据通常有三类脏东西：

  • 非文本噪音：@提及、链接、表情代码、重复刷屏字符；
  • 结构性脏数据：重复抓取的同一条评论、内容为空的行、抓取失败的缺失值；
  • 无信息句子：只有「111」「+1」「沙发」这种没有观点的灌水。
比喻

预处理之于数据分析，相当于洗菜之于炒菜。菜里有泥，后面厨艺再好也白搭。论文里这叫「垃圾进，垃圾出」（garbage in, garbage out）。

1.3小白课先补常识：你和微博之间到底发生了什么

爬虫这个词听着吓人，其实就是「让程序替你去上网刷微博」。要理解它在干什么，先搞懂你平时刷微博时，背后悄悄发生了什么。把微博想成一家网店，把你的浏览器（Chrome / Edge）想成你手里的点单 App：

① 服务器 = 网店仓库
一台 24 小时开机、存放所有数据的大电脑。你发的每条评论最终都存在它这里。
② 客户端 / 浏览器 = 点单 App
你看的微博页面，是浏览器向服务器「下单」要来的。刷一下 = 下一次单，服务器把最新内容「发货」回来。
③ 请求 / 响应 = 下单 / 发货
你点「下一页」，浏览器发出一个请求，服务器回一份响应。爬虫就是写程序自动地、批量地「下单」。
④ 网址 URL = 商品地址
形如 https://s.weibo.com/...?page=2。最后的 page=2 就是「第 2 页」，爬虫改这个数字就能一页页翻。

四个爬虫绕不开的名词（教程里天天出现，这里一次讲透）

登录状态 & Cookie（身份手环）
你在微博登录一次，服务器就给你的浏览器发一条「手环」（Cookie）。之后每次下单，浏览器都自动戴着手环，服务器一看就知道「这是已登录的某某」，才肯把数据给你。爬虫最麻烦的一步，就是把这条手环（Cookie）复制给程序，让程序冒充「已登录的你」去下单。手环会过期，过期就得重新登录再复制。
Profile（浏览器的小抽屉）
你电脑里浏览器存 Cookie、书签、历史的地方就叫一个 Profile（用户配置）。同一浏览器可以开多个 Profile，就像多个互不干扰的小抽屉，各自记各自的登录状态。爬虫教程说「新建一个 Profile / 用无痕模式」，就是想要一个干净、独立的小抽屉，避免和你平时的账号互相干扰。
User-Agent（自我介绍）
浏览器每次下单都会附一句自我介绍：「我是 Chrome 浏览器，Windows 系统」。这句就是 User-Agent。有些网站会看这句话决定给不给内容，所以爬虫常要把自己的介绍「伪装成正常浏览器」。
IP（你的门牌号）
你家网络在网上的地址。若同一 IP 一秒下单几百次，服务器会判定「这是机器人」而封禁。所以爬虫要放慢速度、加延时——这也是 1.6 代码里那句 sleep(2) 的原因。
按 F12 能看到什么（可选体验）

在浏览器按 F12 → 切到 Network（网络） → 刷新页面，你会看到浏览器一条条「下单记录」。点开任一条，在 Headers 里就能找到 Cookie 和 User-Agent 两行——爬虫教程让你「复制 Cookie」，就是从这里复制。看不懂数字没关系，知道「它们就藏在这」即可。

合规红线（写进论文方法部分，答辩必问）

只抓公开可见的评论；不碰他人隐私字段（手机号、真实身份）；遵守网站规则、控制频率不拖垮服务器；数据仅用于学术研究。这些写进论文，体现的是研究伦理，是加分项。

1.9代码清洗三连 + 构建语料库
import re

def clean(text):                       # 把 1.5 演示的规则写成函数
    text = re.sub(r"@[\w\u4e00-\u9fa5]+", "", text)      # 去@
    text = re.sub(r"http\S+|https\S+", "", text)         # 去链接
    text = re.sub(r"\[[^\[\]]+\]", "", text)             # 去[表情]
    text = re.sub(r"(.)\1{2,}", r"\1\1", text)           # 压缩重复字
    return text.strip()

df["text"] = df["text"].astype(str).apply(clean)   # 对整列逐行套用
df = df.drop_duplicates().dropna()                  # 去重、删缺失
df = df[df["text"].str.len() >= 5]                  # 丢掉太短的灌水
df.to_csv("corpus_clean.csv", index=False)          # 保存 → 语料库建成
re.sub 是「查找替换」：第一个参数是暗号（正则表达式），第二个是替换成什么。暗号背不下来没关系，上面 5 行是舆情清洗的“万能五件套”，直接抄进论文附录即可。

# ============ weibo_collector.py · 论文附录完整脚本 ============
# ---------- ① 配置区：只改这里 ----------
KEYWORD = "XX餐厅 吃坏肚子"          # 你的事件关键词
PAGE_MAX = 378                       # 目标约 3 万条：每页 80 条
HEADERS = {
    "Cookie": "粘贴你 F12 复制的手环",
    "User-Agent": "Mozilla/5.0 ... Chrome/120",
}

# ---------- ② 函数：要一页，回一页 ----------
def fetch_page(page):
    r = requests.get("https://s.weibo.com/ajax/comment",
                     params={"q": KEYWORD, "page": page},
                     headers=HEADERS, timeout=10)
    if r.status_code != 200:
        raise RuntimeError(f"第{page}页失败 HTTP {r.status_code}（手环过期？）")
    return r.json()

# ---------- ③ 主循环：一页页下单，随机手速 ----------
rows = []
for page in range(1, PAGE_MAX + 1):
    for c in fetch_page(page)["comments"]:
        rows.append([c["id"], c["text"], c["created_at"],
                     c["like_count"], c["user"]["name"]])
    time.sleep(random.uniform(1.5, 3.5))   # 随机延时更像人类，保护 IP

# ---------- ④ 落盘：utf-8-sig 让 Excel 打开不乱码 ----------
with open("weibo_comments.csv", "w", newline="", encoding="utf-8-sig") as f:
    w = csv.writer(f)
    w.writerow(["id", "text", "time", "likes", "user"])
    w.writerows(rows)
print(f"采集完成：{len(rows):,} 条 → weibo_comments.csv")

1.21讲解 · 代码SimHash 位级真实算法：64 bit / SHA1 / 加权投票 / 海明距离

1.16 已经演示了 SimHash 的直观效果；这一格把 backend/services/text_dedupe.py 里的真实算法摊开——每一条文本怎么变成一个 64 位整数、两条怎么算海明距离、分组用什么策略。

# ① 指纹位宽：64 bit（工程惯例，够用且能塞进一个 uint64）
_BIT_WIDTH = 64

# ② 每个 token → 一个 64 位整数（取 sha1 前 8 字节，大端转整数）
def _token_hash(tok):
    return int.from_bytes(hashlib.sha1(tok.encode("utf-8")).digest()[:8], "big")

# ③ 一条文本的指纹：每个 token 对 64 个 bit 位「投票」
#    权重 = token 词频；bit=1 → 该位 +1×w，bit=0 → 该位 -1×w；最后取符号
def _simhash(text):
    votes = [0]*64
    for tok, w in Counter(tokens(text)).items():
        h = _token_hash(tok)
        for i in range(64):
            votes[i] += w if (h >> i) & 1 else -w
    return sum((1<<i) for i,v in enumerate(votes) if v>0)

# ④ 海明距离：XOR 后 bit_count——两个指纹有多少位不一样
def hamming(a,b): return (a ^ b).bit_count()

# ⑤ 分组：不是两两比对（那样 O(n²) 会爆），而是「分带 pigeonhole」加速
MAX_BANDED_DISTANCE = 15          # 支持 ≤15 位的近似搜索
# dedupe_similar 节点里 max_distance 由参数指定；本项目工作流 JSON 用 8
为什么 SHA1 而不是 MD5
SHA1 的分布更均匀、冲突少；这里不涉密码安全、只用它的「均匀性」。取前 8 字节刚好塞满 64 位。
为什么「投票」而不是「叠加」
简单 XOR 叠加会互相抵消；加权投票让「高频词」把 bit 拉到自己那侧，最后取符号——语义相近 → 关键 token 相同 → 大多数 bit 相同。
为什么 max_distance 是 8 而不是 3 或 15
64 位里差 ≤8 ≈ 相似度约 87.5%。阈值 3 太严（换个人称就漏检），阈值 15 太松（正常写作也可能撞车）。8 是网暴场景的经验值——项目里 dedupe_similar 节点的 JSON 参数就是 8。
MAX_BANDED_DISTANCE = 15 是什么
分带搜索算法能高效查出的最大距离上限。8 ≤ 15，所以工作流用 8 完全没问题；若有人想调 20，代码会拒绝并给「按名拒绝」错误——静默改成 15 会更糟。
一句诚实的话

SimHash 分组后「保留先到的那条」——同一批文件在不同合并顺序下，各阶段行数会略有出入。教程与论文里所有引用行数都是在本项目画布的上游合并顺序下测得的。换顺序重测对不上时，应怀疑顺序变了而非数据变了。

1.22讲解 · 演示两套 checkpoint：节点级指纹 与 逐行 item_seen 台账

「断点续跑」不是一个笼统的机制，项目里其实同时跑着两套——一套服务分析、一套服务采集。它们存的东西、失效规则都不一样：

A. 节点级指纹
（服务 DAG 分析链）
SHA1(节点类型 + 操作 + 参数 + 上游指纹)。存在 SQLite data/runs.db 的 node_runs 表。命中规则：状态 ∈ {DONE, RESTORED} 且 指纹一致 且 行数 > 0 且 类型 ≠ source。改一个参数 → 指纹变 → 该节点和所有下游节点重跑；上游没动的旁支照旧跳过。
B. 逐行 item_seen 台账
（服务爬虫采集）
SQLite data/runs.db 里一张表，主键 (scope, item_key)。scope = "item:" + 节点指纹，item_key = 微博 ID / 评论链接。命中就跳过、未命中就抓。断网、封号、Ctrl+C 都没关系——重启后从台账知道哪些抓过、不重复消耗账号。
为什么两套不能合
分析节点的产物是整表（一个 SHA1 就代表它跑对了）；采集的产物是一行一条真实微博（改一次参数不会让已抓的 5 千条评论作废，抓都抓到手了）。合成一套要么浪费、要么丢数据。
LLM 单独还有一份
LLM 调用（比如主题概括 topic_label）走 RowCheckpoint / RowCache——按 text_hash 落 JSONL 到 data/checkpoints/。断点续跑不重新付费。三份机制并存、各司其职。
「成本—迭代分离」的底层

采集（A+B 里的 B）一次做完就锁在台账里；分析（A）改参数就重跑，一次约 18 分钟可反复迭代；LLM 概括按 text_hash 缓存、付过一次不再付。这套「三种 checkpoint 各管各」的安排，把「不可逆的采集成本」和「廉价的迭代成本」在物理层就分开了——这是采析绘最工程化的一个决定。

# _build_urls → _generate_hourly_urls（真实代码）
def _generate_hourly_urls(self, start, end, kw):
    urls, cur = [], start
    while cur < end:
        nxt = min(cur + timedelta(hours=1), end)   # 每个小时一段
        SS  = int(cur.timestamp()*1000)             # 微博要毫秒时间戳
        ES  = int(nxt.timestamp()*1000)
        urls.append(
            f"https://s.weibo.com/weibo?q={quote(kw)}"
            f"&timescope=custom:{SS}:{ES}&Refer=g")
        cur = nxt                                    # 不合并、不细分——一小时一片
    return urls

3.1讲解TF-IDF：找出一条评论的「独家关键词」

给你一条评论：「这家餐厅的卫生太差，吃坏肚子了，已投诉」。哪些词最能代表它？「的」「了」显然不算——人人都说的词没有信息量；只在少数评论里出现的词才独家。TF-IDF 就是把这句直觉变成分数：

TF · 词频
这个词在本条评论里出现几次
出现越多越重要。白话：这条评论反复念叨什么，什么就是重点。
DF · 文档频率
多少个评论里出现了这个词
越普遍越不重要。白话：人人都说的词，说了等于没说。
IDF · 逆文档频率
DF 的倒数取个对数
越稀缺越加分。白话：「10 要乘几次才得到某个数」——对数只是把「稀缺」折算成温和的加分，防止生僻词过分膨胀。
TF-IDF = TF × IDF
本条说得多 × 全局说得少
两个条件同时满足 → 高权重 → 这就是这条评论的关键词。

3.4讲解LDA：每条评论都是一锅「主题混合汤」

TF-IDF 一次只看一个词，而 LDA 回答更大的问题：这批评论里其实混杂着几股「话题流」？每条各沾了多少？

把它想成调汤：本次事件其实有三锅「主题原汤」——T1 食品安全与卫生、T2 维权与投诉、T3 口味与性价比。每一条评论都是打汤的人从三锅里各舀几勺兑出来的：有人「卫生 70% + 投诉 30%」，有人「口味 60% + 卫生 40%」。LDA 做的事，就是倒推每个碗里的配比，以及每锅汤里都放了哪些料（高频词）。

  • 你唯一要定的参数：几锅汤（主题数 K）。定 K 靠人眼反复试 + 看生成的词表是否「说得通」——这是文科判断力大放异彩的地方；
  • LDA 不需要人工标注、不懂对错，它只是「发现这批话天然聚成几堆」；
  • 对每个阶段（②划分的五段）分别跑一次 LDA，比较各堆占比的变化 —— 这就是「主题演化」。

3.9实战代码分阶段 TF-IDF：产出论文「各阶段特征词表」

3.3 的代码只跑了全库一次；论文要的其实是每个阶段各自的 TOP10 特征词（这就是「主题演化」的证据表）。加一层 for 循环按阶段分组即可。

import jieba, pandas as pd, numpy as np
from sklearn.feature_extraction.text import TfidfVectorizer

STOP = {"的","了","是","我","也","都","很","就","在","有","这","啊","吗","呢","不","没"}
df = pd.read_csv("corpus_clean.csv", parse_dates=["time"])
sp = pd.read_csv("stage_split.csv", parse_dates=["date"])
stage_map = dict(zip(sp["date"].dt.date, sp["阶段"]))   # 日期 → 阶段 的对照字典
df["阶段"] = df["time"].dt.date.map(stage_map)          # 给每条评论发一张「阶段身份证」

def cut(t):
    return " ".join(w for w in jieba.cut(str(t)) if w not in STOP and len(w) > 1)

rows = []
for st, g in df.groupby("阶段"):                    # 五个阶段各跑一遍
    vec = TfidfVectorizer(max_features=100)
    m = vec.fit_transform(g["text"].map(cut))
    top = np.asarray(m.mean(0)).ravel().argsort()[::-1][:10]   # 平均分从高到低取 10 个
    rows.append([st] + [vec.get_feature_names_out()[i] for i in top])

out = pd.DataFrame(rows, columns=["阶段"] + [f"TOP{i+1}" for i in range(10)]).set_index("阶段")
print(out.to_string())
out.to_csv("stage_keywords.csv")                    # → 论文表 2

3.7 教你训练模型；这一格补完最后一公里：把每条评论的主题占比按阶段取平均，得到论文核心矩阵 topic_evolution.csv（3.6 演示里那张表就是它画出来的）。

import jieba, pandas as pd
from gensim import corpora
from gensim.models import LdaModel

df = pd.read_csv("corpus_clean.csv", parse_dates=["time"])
sp = pd.read_csv("stage_split.csv", parse_dates=["date"])
stage_map = dict(zip(sp["date"].dt.date, sp["阶段"]))
df["阶段"] = df["time"].dt.date.map(stage_map)

STOP = {"的","了","是","我","也","都","很","就","在","有","这","啊"}
texts = [[w for w in jieba.cut(str(t)) if w not in STOP and len(w) > 1] for t in df["text"]]

dic = corpora.Dictionary(texts)                     # 发工牌
corpus = [dic.doc2bow(t) for t in texts]            # 每条评论 → (词号,次数) 清单
lda = LdaModel(corpus, num_topics=3, id2word=dic, passes=20, random_state=42)

dist = pd.DataFrame([dict(d) for d
        in lda.get_document_topics(corpus, minimum_probability=0)]).fillna(0)

3.19讲解 · 代码「一致性」到底怎么算的：NPMI 逐对公式（topic_coherence）

3.12 讲了 argmax 陷阱，但没讲「一致性」本身是怎么算出来的。它是 NPMI（归一化逐点互信息）。项目里的实现（data_analysis.py:2168）：

# 对一个主题的 top-10 特征词，逐对 (i,j) 算：
p_i = doc_with_i / total_docs
p_j = doc_with_j / total_docs
p_ij = doc_with_both / total_docs
npmi(i,j) = (log2(p_ij) - log2(p_i) - log2(p_j)) / (-log2(p_ij))
#   分子 = PMI（两者一起出现比独立出现「超预期」多少）
#   分母 = -log2(p_ij)，做归一化让结果落在 [-1, +1]
# 主题分 = 每对 NPMI 取平均；全库分 = 各主题分再平均
参数（工作流 JSON 实际值）
min_topics=2 · max_topics=8 · topn=10 · coherence_max_documents=0（全量、不抽样）· tfidf max_features=2000。全样本和五个阶段各扫一次，共 6 处 topic_coherence 节点。
为什么要 max_documents=0
抽样扫描会让 argmax 随表格行序漂移——3.12 的「一致性 argmax ≠ 最优」这条陷阱，一半就来自默认抽样。为某阶段定 K 的那次扫描必须用该阶段全量数据。
NPMI 的直觉
如果主题里两个词「几乎总是一起出现」→ p_ij 大 → NPMI 接近 1（一致性好）。如果「各自都常见但很少同时出现」→ p_ij 很小 → NPMI 接近 -1（主题割裂）。+1 = 强绑定，0 = 独立，−1 = 互斥。
常见误解：一致性高就是好主题？
不一定。主题越少，越容易把泛词分到一组，NPMI 反而高。所以 3.12 强调 K=2 有时一致性最高——那是模型在偷懒。必须与「主题可辨识度」「困惑度」并列看。
3.20讲解 · 代码主题距离图不是 PCA，是 JSD + Torgerson MDS（topic_map）

3.18 说「主成分分析」是一种通俗说法；真实实现是两步：先算两两主题的 JSD（Jensen-Shannon 散度）距离矩阵，再做 Torgerson 经典 MDS 降到二维。原因：PCA 作用在向量上、JSD 定义在概率分布上——LDA 输出的是分布，PCA 直接用不合适。

# data_analysis.py:1749 真实流程
# ① 主题 × 词 分布 → 两两 JSD 矩阵（对称、有界、可微）
D[t1,t2] = JSD(phi[t1], phi[t2])          # phi 是主题的词分布
# ② Torgerson 经典 MDS：对距离阵做双中心化求特征向量
J = -0.5 * H @ (D**2) @ H                  # H = 中心化矩阵
eigvecs = top-2 eigenvectors of J, scaled  # → (x, y) 坐标
# ③ 气泡大小 = 主题流行度 = doc_topic.sum(axis=0)
为什么用 JSD 不用 KL

KL 散度不对称、且对 0 概率敏感；JSD 是 KL 的对称化版本、有界、永远良定义——两个维度量对称性更好的东西时用它。这是「主题距离」这件事的标准做法。

写论文时的正确术语

「对主题-词分布矩阵两两计算 JSD，采用 Torgerson 经典多维标度法降至二维平面，气泡面积映射主题流行度。」——这一句精确、可复核、比「PCA 气泡图」严谨。

3.21讲解 · 代码桑基边的相似度：1/(1+JSD)，阈值 0.5 才画（topic_flow）

3.16 讲了桑基的直觉；真实实现（data_analysis.py:2028）只一行公式：

similarity(t_stageA, t_stageB) = 1 / (1 + JSD(phi_A, phi_B))
# JSD ∈ [0, 1] → similarity ∈ [0.5, 1]
# 完全相同 → sim=1；完全不同 → sim=0.5
edges = [(A,B,sim) for (A,B) in adjacent_stages if sim >= min_similarity]
工作流参数
min_similarity = 0.5（node-56）· 边连接相邻阶段（不跨阶段）。注意：min_similarity=0.5 意味着 JSD ≤ 1 都算，几乎所有对都会保留；论文里说「最强迁移 0.912」是具体边的观测值，不是筛选阈值。
为什么是 1/(1+x) 而不是 1−x
1−JSD 会在 JSD=1 时给 0，容易把边完全切断；1/(1+x) 更「软」，即使主题彻底不同也保留 0.5 的下界——画桑基时能看到「迁移弱」而不是「看不到边」。
边的粗细
桑基边的粗细一般用两个主题的 doc_n 交集或前后阶段的相对权重（工作流里 flow_weights_col 指定）。教程 3.16 的示意简化了这点。
连续谱系 vs 断裂更替
「连续」的证据是——即使换了阶段，最强边的 similarity 也远高于最低阈值；「断裂」则会出现整列阶段之间几乎无边。论文说「连续谱系」就是基于这个观察。
3.22讲解 · 代码显著词的 Sievert-Shirley relevance 公式（topic_salience）

3.14 讲了「全库频次 vs 主题内频次」的直觉；真实公式叫 Sievert-Shirley relevance，是论文 Interactive TopicModels (2014) 里的标准式：

relevance(w, t) = λ · log2 p(w|t) + (1 − λ) · log2 ( p(w|t) / p(w) )
#        ↑ 主题内的绝对频率        ↑ 相对全库的「抬升倍数」(=PMI 的分子部分)
λ = 1 时
只看主题内频率 → 高频词优先，会列出「的、了」这种（分词后停用词已被过滤，但仍偏向本主题最常见词）。工作流节点 50/76/83 用 λ=1（阶段/全库定标）。
λ = 0 时
只看相对抬升 → 稀有但独特的词优先，会列出「京报、学州、遗书」这种只在特定主题出现的词。
λ = 0.5 时
两者平衡——「在本主题里也常见、且相对全库明显抬升」的词胜出，最适合写进论文。node-42（全样本演示）用 λ=0.5。
参数（真实值）
topic_max_features=2000 · topic_topn=30（不是 7）。工作流里 λ 在不同节点上取 0.5/1，是「同主题两种视角交叉」的一种稳健做法。
为什么这个公式重要

它把「显著」这件事从「凭印象挑几个词」变成一个可参数化的连续旋钮：λ 从 0 到 1，你在「独特性」和「常见性」之间滑动。写论文时把 λ 报出来，别人就能复算。这是「方法可复核」的最小成本。

像阅卷老师一目十行扫重点短语：不逐字读，而是三个词一组「滑」过去，专门捕捉「太失望」「不接受道歉」这类固定搭配的局部特征。快，且认得出常见情绪句式。
BiLSTM（双向长短期记忆）· 前后文都读
像仔细的同学从左往右读一遍，再从右往左读一遍，并且记得前面读过什么。「本来以为会赔偿，结果商家否认」——读到「否认」时还记得「以为」，才能体会落差。双向 + 记忆 = 上下文理解。
Attention（注意力）· 圈重点
像最后拍板的主编，给句子里每个词分配注意力份额：判断情绪时「失望」「道歉」各占三成，「今天」「我们」几乎不看。下一格你可以亲手拨这个「注意力旋钮」。

三者串联：CNN 抓短语特征 → BiLSTM 把特征串成上下文理解 → Attention 挑出最影响判断的词 → 输出三个分数（积极/中性/消极），谁最高听谁的。

4.8实战代码CNN+BiLSTM+Attention 完整模型（方法章素材）

4.5 用的是「预训练模型」（省事版）；开题表写了 CNN+BiLSTM+Attention，方法章最好能展示这个模型本身。下面 30 行就是它的完整定义——每一行注释都对应 4.2 的一个比喻，看懂结构即可，训练可交给导师/学长。

import torch, torch.nn as nn

class SentimentNet(nn.Module):
    """CNN 抓短语 → BiLSTM 读上下文 → Attention 圈重点 → 三分类"""
    def __init__(self, vocab_size, emb=128, hid=128, n_class=3):
        super().__init__()
        self.emb    = nn.Embedding(vocab_size, emb)              # 每个词查成 128 维向量
        self.cnn    = nn.Conv1d(emb, hid, kernel_size=3, padding=1)  # 三词一组扫短语
        self.bilstm = nn.LSTM(hid, hid, batch_first=True, bidirectional=True)
        self.attn   = nn.Linear(hid * 2, 1)                    # 给每个词打一个分
        self.fc     = nn.Linear(hid * 2, n_class)               # 出口：三个分数

    def forward(self, x):                       # x: 一批句子的词号 (批, 句长)
        h = self.emb(x).transpose(1, 2)          # (批,词,向量) → (批,向量,词)
        h = torch.relu(self.cnn(h)).transpose(1, 2)   # 短语特征
        h, _ = self.bilstm(h)                   # 每个词都带上了双向上下文
        a = torch.softmax(self.attn(h), dim=1)   # 注意力份额：全句加起来 = 1
        ctx = (a * h).sum(dim=1)                # 加权平均 = 整句摘要向量
        return self.fc(ctx), a.squeeze(-1)       # 预测分数 + 每词权重(画图用!)

4.12讲解三个同源模型互证：极性 · 细粒度情绪 · 立场

情感不是一个维度。系统里其实跑了三个同源的微调 BERT，让它们从不同角度互相印证，但论文「情感演化曲线」以第一个（极性）为准。

bert_sentiment · 极性
积极 / 中性 / 消极三分类 + 情感强度——主曲线用它，回答「大家整体情绪是好是坏」。
bert_emotion · 细粒度情绪
SMP2020-EWECT 多分类（愤怒、悲伤、恐惧、开心……），回答「具体是哪种情绪」，比三分类更细。
bert_tendency · 立场倾向
由大模型蒸馏标注、再用 BERT 承接的立场分类，回答「站在哪一边」——情绪 ≠ 立场，二者要分开。
为何要互证
三个口径相互交叉能防止「一个模型说了算」。论文里用一句话交代主口径（极性），其余作为稳健性佐证即可。

底座 + 语料只提供「正/负」两种标签。所谓「中性」，是让概率落在 0.4–0.6 之间由阈值判出来的——不是模型直接吐「neutral」。这一条很多论文会误写成「三分类模型」，答辩被追问就露馅。
关键选择：0.05 验证 + 无分层
95% 训练 / 5% 验证，seed=42。没 stratify 意味着验证集里正负比不一定等于训练集——脚本作者选择「简单可复现」，代价是评估数字有一点点抖动。
关键选择：最佳模型用 f1_macro 挑
每 epoch 跑一次验证，只保留 F1 宏平均最高的那个 checkpoint。因为类别略不均衡时 accuracy 会被多数类带偏，F1_macro 更诚实。
关键选择：整套超参是「保守派」
lr=2e-5 / batch=16 / epoch=3 / warmup=0.1 / weight_decay=0.01——这是 BERT 微调的社区默认，不炫技。能复现就是好配置，答辩问「为什么不精调」答「精调会让不同种子跑出不同结论，反而不稳」。
论文里怎么写这一句

「情感判别模型采用 hfl/chinese-roberta-wwm-ext 作基座，在约 10 万条微博正负情感语料（weibo_senti_100k）上做二分类微调（max_length=128, batch=16, epochs=3, lr=2e-5, warmup=0.1, weight_decay=0.01, fp16）；以 95/5 分层，seed=42，每 epoch 验证一次并按宏平均 F1 选最佳 checkpoint。」——一句话就把「怎么微调」写清了。

4.20讲解 · 演示学生的天花板 = 老师的 kappa：蒸馏的诚实边界

蒸馏出来的学生不可能超过老师——因为它学的就是老师。怎么量化这条天花板？用 eval_teacher_ceiling.py：先人工给 360 条留出集打标签，再让老师 Qwen 打同样这批，然后算老师与人工的一致率（Cohen's kappa 和 raw agreement）。这条一致率就是学生能达到的上限。

# eval_teacher_ceiling.py 关键流程（真实项目）
hold = pd.read_csv("datasets/tendency_holdout_labeled.csv")
       # 三列：text, distilled_label(老师给的), human_label(人工给的)
po = (hold.distilled_label == hold.human_label).mean()   # 观察一致率
kappa = (po - pe) / (1 - pe)                             # 减去「随机也能蒙对」的部分
# 输出：raw agreement / kappa / 每类召回与精确率 / 人工×老师混淆矩阵
# 明确打印："no distilled BERT should be expected to beat ~po"
为什么 raw agreement 不够
如果老师总是猜多数类，也能蒙对 60%。Cohen's kappa 减掉随机基线，剩下的才是「老师真的懂」。这是答辩高频追问。
kappa 高不等于学生一定高
学生只能逼近老师，且取决于训练语料覆盖度。蒸馏语料只有 8 千条、且全部由「老师觉得能标清楚的」组成，某些罕见类老师自己都标不稳，学生学到的是「不确定」——所以 v2 才补上类权重和 focal loss。
论文里怎么写
「立场六分类模型由本地大模型 Qwen3.5:9b 蒸馏训练；留出集上老师与人工的 Cohen's κ=X.XX 构成学生模型的表现上界，最终模型 macro-F1=X.XX 逼近该上界。」——不吹不黑。
这条上限还能被反过来利用
如果学生某类比老师还高——不要高兴，通常是留出集样本太少撞对了；应先怀疑数据而不是庆祝。
4.21讲解软标签为什么放弃 · 自训练做了什么：两次实验记录

项目 README 里有一行「已放弃」——这是研究者诚实的痕迹。为什么放弃？先看它原本想做什么。

软标签蒸馏（distill_tendency_softlabel.py，已放弃）

硬标签 = 老师给一个最终答案；软标签 = 老师采样 5 次（temperature=0.6），统计 5 次里每类出现频率，得到一个概率向量 prob_Anger=0.3, prob_Joy=0.5…，学生用 KL 散度去逼近这个向量。

为什么放弃

采样 5 次的老师输出仍然系统性地自信过头——它对反讽句五次都说「反讽」，其实人工看会犹豫。软标签把这种过度自信蒸给了学生，反而让 BERT 学生学得更「自信」而不是更「稳」。留档但不进主链。

自训练 / 伪标签（selftrain_tendency.py）

用已经训练好的学生，去给没标签的微博打标签。信心足够高（softmax 概率 ≥ 0.9）就收下，加进训练集重训一轮。

  • 初始标签集：8,209 条蒸馏（95% 训练 7,798 / 5% 验证 411）
  • 无标签池：weibo_clean_265k 里没进语料的 10,000 条、长度 ≥ 4
  • 信心阈值：--thr 0.9（低于此丢弃）
  • 迭代次数：2 轮（基线 + 1 次自训练）
  • 噪声底：±0.011（论文数字必须大于这个才叫「有增益」）
诚实的写法

「伪标签在阈值 0.9 下引入额外 N 条样本，重训一轮使 macro-F1 从 X.XX 变到 X.XX，差异未超噪声底 ±0.011，视为无显著改善，最终模型未采纳自训练版本。」——这就是「做了实验但没用」的诚实交代，比只报最好的数字可信得多。

4.22讲解 · 演示留出集是怎么「爬+标」出来的：360 条 = 6 类 × 60

学生 BERT 到底好不好，不能拿蒸馏语料自己考自己（老师已经标过一遍，学生学了再去考当然高分）。所以需要真实爬取 + 人工标注的留出集。项目里这条链是：

  1. 爬（crawl_controversy.py）：不写爬虫，直接调用自己平台的 API——boot app.py:5000 → POST /api/workflow/execute → 轮询状态。第一段抓帖子（默认关键词「网暴」、60 条）、第二段每帖翻 15 条评论、25 个帖开。真实产出：controversy_crawl.csv 2,137 行（text, keyword, source_url, crawled_at——可回溯）。
  2. 标（人工）：把 2,137 条按六类人工标注 → controversy_labeled.csv 2,080 行。
  3. 抽（make_holdout.py）：从蒸馏语料每类抽 60 条 seed=42 → 输出 tendency_holdout_template.csv 360 条，列 text, distilled_label, human_label（human 空着等人工填）。注意：这一步抽出模板时并没有从训练里去重，去重发生在 v2 训练时（v2 trainer 主动剔除与 holdout 交集）。
  4. 填 human_label → 得到 tendency_holdout_labeled.csv，交给 eval_teacher_ceiling.py 算 κ。
为什么「爬留出集」要走 app 的 API

为了留出集和生产数据同源——同一段 crawler 代码、同一份风控策略、同一份 Cookie 台账，采集偏差一致，学生与真实分布的差异才有意义。不能手写脚本另起炉灶，否则测出来的「留出」和生产根本不是一件事。

4.23讲解词袋基线：train_sklearn_ml.py—— 为什么要用 BERT，先要有对照

答辩最容易被追问的一句是：「为什么不直接用一个简单的分类器？你证明 BERT 更好了吗？」项目里的答案就是这份 sklearn 对照。train_sklearn_ml.py 用的是最经典的组合：

LogisticRegression(max_iter=3000, C=6.0, class_weight="balanced")
  ↑ 简单、可解释、训练秒级
TF-IDF(max_features=100000, ngram_range=(1,3))
  + char-level FeatureUnion（词 + 字双通道，抗分词错误）
train_test_split(test_size=0.15, stratify=y, random_state=42)
能训的目标
sentiment（正负）+ emotion（五类，surprise 被丢弃——公开语料里样本太少）。tendency / aggression 不训，前者缺语料、后者用规则更合适。
产物
MODEL_DIR/<name>.pkl——一个 pickle 文件几百 KB，比 BERT 小两个数量级。可解释性极好：可以看 LogReg 每个特征词的权重。
意义一：证 BERT 值得
如果 BERT 只比 LogReg 高 0.5% —— 说明「词袋就够了」，应该改用简单模型。真实情况是 BERT 大幅领先，才站得住「为什么不用简单模型」。
意义二：给「模型选型」留退路
如果服务器资源有限、或要跑大批量、或要完全可解释——LogReg 版仍在。工程上「留一手」不是不自信，是稳健性。
论文写法

「为验证微调 BERT 相对传统机器学习的增益，本研究同时训练了 TF-IDF(词+字, max_features=100k, ngram 1-3) + LogisticRegression(C=6.0, class_weight=balanced) 基线，留出集上……」——这一段一放，答辩追问就没了。

4.24讲解技术选型：为什么这三类分析用「微调 BERT」，而不是直接调大模型

系统本就常驻一个本地大模型（Qwen3.5:9B，见 3.13 主题概括）。那一个自然的问题是：情感 / 情绪 / 立场这三类分析（4.12），为什么不一步到位、直接把这个大模型当分类器，而要额外微调一个 BERT？答案分两层——先说为什么不能用随便一个通用情感工具，再说为什么是微调 BERT、而不是那个更大的 Qwen。

（一）领域必须匹配，通用工具会系统性跑偏
SnowNLP 在电商评论上训练，把微博上的控诉、反讽、哀悼成批误判为「积极」（4.10 那次纠偏）。可见在一个有明确领域、明确标签集的任务上，通用工具的「泛」是缺点不是优点。而微调 BERT 学的就是微博上的判断；立场六类的标签更是直接由大模型在 26 万条真实微博上蒸馏得到——「学生的老师就是那个大模型」。所以在这一个窄任务上，专用小模型并不比通用大模型差：参数量大，不等于在我们这几类标签上判得更准。
（二）输出是「类别」，不是「文本」
分类只要「看一眼、报个类」，一次前向即出各类概率（pipeline 直读模型的 id2label，结构化、可按名拒绝、绝不臆造标签）；大模型却要逐字「生成」一个答案。这决定了两者的计算形状根本不同：前者与输出长度无关、可整批一次算完；后者按 token 自回归解码、逐行往返。

第二点在速度上几乎是压倒性的。下表是采析绘平台在同机上的实测：

后端吞吐（实测）每行耗时30,235 条评论耗时
微调 BERT（微博域）约 237 行 / 秒约 4 毫秒约 2 分钟
通用大模型 Qwen3.5:9B（逐行）约 0.3 行 / 秒约 3.4 秒约 29 小时
质量：窄任务上不输
本项目留出集实测——情感 accuracy = 宏平均 F1 达 0.9785；情绪六类 acc 0.731 / 宏 F1 0.681；立场六类宏 F1 0.668。对照 SnowNLP 系统性跑偏，「专用微博模型」正是把质量拉回正轨的那一步。
速度：相差近 800 倍
BERT 约 237 行/秒，逐行调大模型约 0.3 行/秒。3 万条评论交给 BERT 约 2 分钟扫完，交给 Qwen 逐行要二十多小时——这就是「让大模型逐行读几万评论」在工程上不可行的原因。
成本与确定性
大模型逐行既慢、又要常驻 GB 级权重、还输出非确定的自由文本；BERT 本地一次前向、同进同出，同一行每次给同一标签——这正是断点续跑与缓存复算的前提。
分工，而非替代
需要生成与深度判断的环节仍交给大模型：主题概括（topic_label）、语义清洗、跨行结论都走 Qwen3.5:9B；只把「封闭标签集的逐行分类」这类量大、要求确定性的活交给微调 BERT。
「新的大模型」不等于更好

选型看的是这个任务上的实测，不是发布日或参数量。本项目亦实测：换更新的骨干反致退步（gte-base-zh 宏平均 F1 更低）、英文 ModernBERT 的 tokenizer 对中文直接失效。

写进论文（选型理由）

「情感 / 情绪 / 立场三类逐行分类采用领域微调 BERT，而非直接调用通用大模型：其一，任务有明确领域与封闭标签集，通用模型存在领域偏移；其二，输出为类别而非文本，判别式模型一次前向即可整批推断，实测吞吐较逐行生成高约三个数量级，且输出确定、可缓存复算。生成类子任务（主题概括等）仍交由本地大模型完成。」——这一段一放，「为什么不用现成大模型」的追问就落地了。

实测环境：RTX 4060 Laptop、torch + cu126 / transformers、fp32、batch 32、max_length 512；大模型数为串行、单条、输出被约束为极短的逐行样本，绝对值随是否开启思考链与批量配置浮动，但一到两个数量级的差距由「计算形状」决定，不会翻转。完整复现见项目 docs/why_finetuned_bert.md。

5.1讲解图谱是论文的「脸面」

前四个环节产出了三样东西：阶段切分（②）、各阶段主题占比（③）、各阶段三类情感占比（④）。可视化环节的任务只有一个：把它们叠在同一张图上，讲出完整的故事。

经典做法是堆叠面积图：横轴时间、纵轴占比（三块加起来永远是 100%），三种颜色（本教程用三种线纹图案，保持黑白美学）随时间此消彼长——消极面积什么时候膨胀到最大、什么时候开始退潮、什么时候和积极面积交叉，全部一目了然。

答辩老师翻你的论文，第一眼看摘要，第二眼看的就是这张图。图的规范：坐标有单位、图例能自明、阶段边界用虚线标出、结论能写进图题。

「本研究以『××事件』微博评论区为数据源，利用 Python 爬虫采集 ×× 至 ×× 期间评论 N 条，经去重、去噪及无效文本过滤后获得有效语料 M 条。以每日评论量构建时间序列，结合舆情生命周期理论与热度阈值法（阈值取峰值的 X%），将事件划分为潜伏、爆发、蔓延、衰退、长尾五个阶段。采用 TF-IDF 提取特征词，借助 Gensim 构建 LDA 主题模型（K=3），识别各阶段主导议题；采用 CNN-BiLSTM-Attention 深度学习模型对语料进行三分类情感判别（积极/中性/消极），并经人工抽检 300 条修正，一致率 X%。最终以 matplotlib 绘制情感演化图谱，呈现舆情情绪的阶段性演变特征。」

常见误区（答辩高频被问）
  • 只报占比不报样本量——「消极占 70%」若来自 10 条评论则毫无意义；
  • 阈值/K 值拍脑袋且不交代——参数要在方法部分写明并做简单敏感性说明；
  • 把相关当因果——「道歉后消极下降」不等于「因为道歉而下降」，结论措辞要克制；
  • 图表无单位、无图例、截图糊——导出统一 300 dpi。

5.11讲解画布怎么把数据变成图：节点编排 · ECharts · 列名契约

compile + visualize 节点
compile 把上游结果整理成绘图所需的数据结构，visualize 节点声明「用哪张图、读哪些列」。BERT 主链里有 23 个 compile、23 个 visualize。
ECharts 渲染引擎
图表由 ECharts 引擎绘制，可导出 PDF（矢量、适合印刷）与 PNG（带哈希后缀），同时导出配套 CSV 数据表与文本表。
列名契约
步骤的输出列名就是图表的输入列名（如主题距离图读 pc1/pc2/topic/prevalence_pct）。列名以参数声明，缺列会直接拒绝。
为什么这样很稳
任何一侧改了列名，另一侧会报「具名拒绝」，而不是悄悄画出一张空白图——错误当场暴露，不留隐患。

6.2讲解把「工程性」写进方法：可复现 · 可回溯 · 断点续跑 · 成本分离

这些听起来像「软件的事」，其实都是研究质量的事。答辩老师问「你这结果能不能重跑验证」，靠的就是下面四条：

可复现
同一条链、同样参数，换台机器也能跑出一样的表与图（random_state 等固定住）。
可回溯
每个最终数字都能反查到「哪个节点、按什么规则、在哪张中间表」产出的。
断点续跑
采集中断是「续采」不是「重爬」；分析链可从任意节点恢复，省掉大量沉没成本。
成本—迭代分离
最贵最不可逆的采集只做一次；分析一次约 18 分钟，可反复换参数 / 换模型 / 换阶段重跑。
文科生的 takeaway

你不必亲自写这套平台，但论文方法部分主动交代「数据可回溯、分析可复现」，会让研究可信度上一个台阶。如果条件允许，选一个能导出中间表、能重跑的工具链，比手工 Excel 稳健得多。

6.5讲解 · 演示相关≠因果，以及「只有 5 个点」的显著性陷阱

汇报里有一条结论：「舆情热度与情感强度呈反向关系」。它到底成不成立？两个坑要避开：① 相关不等于因果；② 「反向」不等于一条干净的全局线性相关。按五阶段算，皮尔逊 r 新稿 ≈ -0.42、旧稿 ≈ -0.49，方向为负；可一旦换成论文真实的每日数据（图17，n=80）去算全局线性相关，r 竟≈ 0！这说明所谓「反向」不是直线关系，而是一种对照机制——低声量时段会冒出头发的强度尖峰（如 2/22 声量仅 3 条、情感强度却冲到 0.9943）。切换粒度亲眼验证：

数据粒度 按 5 阶段按每日序列 Pearson r-0.42
按 5 阶段：r ≈ -0.42，方向为负但 n=5 太少；切到「每日」看真实全局线性——几乎为 0。
正确写法（照真实数据改口径）

别把「反向关系」写成「每日显著负相关」——真实每日线性 r≈0，会被自己的数据打脸。稳妥表述：「阶段层面二者方向相反（r≈-0.42，n=5 仅作方向性佐证）；每日层面全局线性相关≈0，所谓'反向'实为特定对照——低声量时段伴随高强度尖峰（如 2/22）。宜作为'低声量·高浓度'的机制描述，而非全局线性断言。」——把「相关/因果」「线性/机制」分清楚，答辩才站得住。

6.9讲解理论地基与研究缺口 · 论文站在哪些前人工作上

方法之外，论文的问题意识来自文献。它把三条线拧在一起，才立住了选题：

群体心理（勒庞）
个体融入群体后，独立判断被匿名性与情绪感染削弱、责任消解——解释了网暴为何"按键伤人"。
风险社会 / 议程设置 / 情感动员
网暴是社会转型期矛盾在网络空间的投射；媒体议程与情感动员共同点燃舆论场。
情感分析技术演进
情感词典 → 机器学习 → 深度学习细粒度识别；常与 LDA 主题模型结合，立体呈现"讨论什么 + 以何种情绪讨论"。
大语言模型（LLM）
零/少样本下把离散特征词凝练成语义标签、规模化替代人工编码——本研究的 Qwen 主题概括即用此。
论文瞄准的三个缺口（= 它的创新点）
  • 既有研究多谈单峰舆情，对网暴「M」型多峰 + 二次爆发的情感冲击与预警着墨少；
  • 少有把 LLM 系统嵌入「采集—清洗—建模—演化—预警」全链路；
  • 网暴治理研究多停留在静态对策，缺少与舆情生命周期阶段的耦合。

本研究正是用「生命周期分阶段 + 情感演化图谱 + 本地大模型 + 微调 BERT」把这三点一次补齐——这也解释了为什么前面每一步都围着"阶段"展开。

6.11讲解 · 演示工作流引擎是怎么「跑」起来的：拓扑排序 · BFS 分层 · 逐节点执行

你在画布上连了 172 个节点、171 条线。点「运行」之后，backend/app.py:_run_single_workflow（app.py:1496）接手。整条执行链只有 4 步，看一遍就懂：

①
校验拓扑 · WorkflowEngine._build_graph + topological_sort（workflow.py:184, 214）
Kahn 算法对 DAG 做拓扑排序，同时检环。有环、缺列名、参数非法 → 立刻拒绝、不开始跑。
②
按 BFS 分层 · group_by_level（workflow.py:242）
入度 0 的节点是第 0 层（一般是 upload / source）；剥掉它们的出边、剩下的入度 0 是第 1 层……一层里节点彼此独立，可以并行跑（ThreadPoolExecutor）。
③
每节点走 _run_node_durable（app.py:4230）
先算节点指纹；若 stored.fingerprint == node_fingerprint AND status ∈ (DONE, RESTORED) AND row_count>0 AND 非 source → 直接复用旧结果（跳过）；否则调 _execute_node（app.py:4417）—— 一个 12 分支的 if-chain，按 node['type'] 路由到 _execute_source_node / _process_node / _analysis_node / _tokenize_node / _visualize_node / _compile_node / _output_node / _resume_node / _upload_node / _name_node / _comment_node。
④
父节点数据传入 · _inputs_for（app.py:1534）
主输入 = 第一个父节点的行；完整父列表也传下去，供 join / fan-in 用。同一层兄弟看到同一份父快照（app.py:1500），确保并行不引发数据撕裂。
这套安排解决了什么

（一）并行度自动——同层节点丢进线程池；用户不用管谁先谁后。（二）断点续跑——指纹命中就跳过；改参数就重跑该节点和所有下游；旁支照旧。（三）失败可局部——失败节点标 NODE_FAILED，其他分支的产物不丢；重跑只补失败的那一支。（四）可回放——每次运行是 data/runs.db 里一条 run 记录，节点级状态、行数、时间戳全在里面。

ml_train/models/ 里的模型不是靠「输入路径」用的——那样容易打错、也不便携。项目里有一份 data/model_registry.json，把 4 个模型登记起来：

6.13讲解 · 演示采析绘的三种「按名拒绝」：宁可拒也不静默错的工程哲学

项目里有一以贯之的设计原则：不猜、不静默改、不假装成功。它体现在三个具体位置——

① 列名契约拒绝
（可视化节点）
visualize 节点的输入列名就是它要求的字段（pc1/pc2/topic/prevalence_pct 等）；上游若改了列名，运行时报「具名拒绝」而不是渲染一张空白图。
对应：5.11、workflow.validate
② 模型按名拒绝
（情感/情绪/立场节点）
选了 ml_train/models/emotion_ewect_six 却给了个不属于六类的标签 → 报错「未知标签」，不 fallback 到默认模型、不返回「中性」糊弄。
对应：6.12、resolve_bert_model
③ 环境按名拒绝
（BERT 依赖检查）
bert 模式缺 torch / transformers → 报错「需要可选依赖 requirements-optional.txt」，绝不悄悄退回 SnowNLP 或规则法。
对应：sentiment.py:53,72
为什么这件事值得单开一格讲
「静默回退」是最危险的 bug 类型——它让结果看起来对、其实错。舆情分析里，一个 fallback 到默认模型的 SnowNLP 输出会像 BERT 输出、但方向完全反（这就是 SnowNLP→BERT 那次纠偏的本质）。按名拒绝 = 让研究者知道系统在哪一步放弃了什么。
论文与答辩的价值

「本研究采用『按名拒绝』原则设计分析工具链——列名、标签集、依赖三项均不做静默回退，任何不匹配都作为具名错误中断当前节点，以保证方法链条每一步都可审计。」这一句把「软件工程的洁癖」讲成了研究方法的一部分。

6.14讲解 · 演示「量级可比」≠「曲线一致」：新旧情感强度对照（旧稿撤下的第二个结论）

6.3 讲了新旧主导极性翻转（积极→消极）——这是最容易发现的一类错误。但情感分析里还有第二类更隐蔽的旧稿陷阱：「量级看起来差不多，就以为趋势也一样」。这一格把汇报 §十三(三) 里的这条诚实说明摊开——

阶段旧 · SnowNLP 情感强度新 · 微调 BERT 情感强度曲线形状
发酵期0.64150.689旧：递增（后段冲上 0.75）
新：持平略降（前高后低，几乎一条横线）

两者量级都在 0.6–0.75，但趋势方向完全相反。
爆发期0.62620.665
波动期0.63780.675
二次爆发期0.67740.665
衰退期0.7515（旧峰）0.662（实为最低）
悬停查看两个模型在各阶段的强度值。

这条被撤下的结论

旧稿基于「衰退期强度最高（0.7515）」写过一句：「本事件情感演化与既有网暴研究呈相反走向——热度退去、情绪反而更强烈。」切换到 BERT 后，衰退期强度反而是全周期最低（0.662）——这条「与既有研究相反」的差异化论点被整段撤下，新稿不再出现。

为什么这件事隐蔽
极性翻转一眼能看到（积极 ↔ 消极）；强度量级都在 0.6–0.75，看起来「数值差不多」，就下意识以为曲线也一样——然后旧稿里基于强度趋势写的那段结论就被无声沿用。这是新旧对照最容易漏的一格。
诚实的写法
「新旧情感强度量级可比（0.6–0.75 区间），但阶段间趋势方向不同——旧稿递增（衰退达峰 0.7515）、新稿持平（衰退最低 0.662）；因此旧稿基于强度趋势得出的『与既有研究相反』这一差异化结论在新稿中撤下，不作延续。」
如何避免这类误沿用
做任何「换模型 / 换数据」的修订时，逐项把旧稿里引用了『强度』这句话的段落拉清单。6.4 的自查表就是这套流程。只要有一处结论是趋势驱动而不是水平驱动，就要单独复核。
呼应 6.3 与 6.5
6.3 讲的是「极性翻转」这条看得见的错；这一格讲的是「曲线形状翻转」这条看不见的错。6.5 的相关 ≠ 因果也提醒过：n=5 阶段点太少、单看趋势不稳——强度差异正好是这条告诫的具体案例。
